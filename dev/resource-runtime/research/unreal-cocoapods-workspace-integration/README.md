# CocoaPods integration into the original UE-generated iOS workspace

Original Darwin CocoaPods 1.16.2 and xcodeproj 1.27.0 completed a real `pod install --no-repo-update` on Linux/Darling stage106, using the existing UE-generated iOS workspace and the local LocalMath Pod. A subsequent native install verified the custom configuration wrappers described below, preserved the first original-project baseline, and exited with outer status zero. These checkpoints establish dependency installation and project/configuration integration. They do **not** establish Pod compilation, UBT linking against the Pod, a built UE App, or completion of the overall build goal.

The game is an ordinary C++ fixture authored by Linuxcode, not an Epic sample project. The preparation helper edits only that fixture's module rules and startup source: the iOS rules consume `LINUXCODE_POD_LIBRARY_DIR` and add `libLocalMath.a` to `PublicAdditionalLibraries`; the startup source calls the fixture's C `local_add(40, 2)`. These are build inputs awaiting execution evidence, rather than proof that the call ran. Engine source and Epic build scripts are not changed. The App target has no ordinary source compilation phase, so adding a framework entry to the App alone would not establish UBT linkage.

The workspace's original game FileRef selects `Intermediate/ProjectFiles/LinuxcodeUESmoke (IOS).xcodeproj`. A separate older `Intermediate/ProjectFilesIOS` project also exists in the private checkout; the helpers deliberately resolve the unique game project from the original workspace instead of adding that second project and another same-named scheme. Original xcodeproj workspace APIs retain all four engine/game FileRefs and add only the Pods project. The original App-to-legacy-target dependency, shared UE scheme, shell scripts, and legacy `XcodeBuild.sh` tool path, arguments and working directory remain verified against the first baseline.

The Podfile uses original xcodeproj subproject and cross-project dependency APIs to make the UE legacy build target depend on LocalMath. Pod target output and the legacy target's exported library directory share `Intermediate/LinuxcodePods/$(CONFIGURATION)-$(PLATFORM_NAME)`, avoiding the different UE and CocoaPods `EFFECTIVE_PLATFORM_NAME` values. This retains the original UE target output layout and the original UBT invocation. The metadata also records original xcodeproj's normalization of two UE fields outside its schema: the legacy target's `productType` and the native target's `passBuildSettingsInEnvironment`. No replacement project parser is introduced.

The first native install exposed a real integration gap: CocoaPods warned that existing custom UE xcconfigs prevented it from assigning its generated base configurations. A successful installation at that point did not prove that settings such as `PODS_ROOT` reached the App. The revised `post_integrate` hook now assigns one App wrapper per configuration. Each wrapper includes the original UE xcconfig first and the matching generated Pods xcconfig second, then adds the shared archive directory to `LIBRARY_SEARCH_PATHS`. If an original native configuration has no base reference, it inherits the project-level configuration of the same name. All original UE xcconfig bytes are checked and left intact. Because the original App xcconfig deliberately clears `CONFIGURATION`, each App wrapper uses its explicit selected configuration name, such as `Development-$(PLATFORM_NAME)`, to find the same archive produced by the Pod and legacy targets. The correction install's JSON verifies all five wrappers, imported Pods settings and original UE file hashes; it does not claim that a linker has consumed those settings. The initial CocoaPods warning describes the configuration before this later hook correction.

`unreal-pods-before.json` is created exclusively on the first installation and read on subsequent Podfile evaluations. This preserves the original UE baseline instead of replacing it with an already integrated project. Verification checks the original targets, source references, original shell-phase hashes, original scheme, original configuration inputs and all original workspace references, while allowing the intentional App wrapper reference changes.

Native operations use the repository's exclusive `runtime/session.lock`. The Python installer keeps that lock throughout installation and evidence capture. Its private per-run launcher inherits the parent's lock descriptor and duplicates it with `exec 9<&FD`, retaining the original `flock 9` operation; `subprocess` passes the descriptor explicitly. Both processes therefore use the same open file description, avoiding a self-deadlock from opening the lock again. The private launcher keeps the original project-root calculation and namespace-script reference, validates a single replacement and a single command occurrence, and records original/private launcher hashes. Linux-only probes cover the profile's timeout wrapper, independent-process exclusion, both parent/child close orders, final release, a missing inherited descriptor and duplicate launcher rejection. Global launchers are unchanged.

The included source consists of the preparation and fresh-install helpers, shared project inspector/configuration integration helper, host-only hook and lock checks, Podfile template, source-input archive helper, and the three existing LocalMath fixture files. Preparation and installation both offer read-only `--check` modes. Installation requires the private, verified runtime profile, the original tools and an already generated UE workspace; this source package does not supply those dependencies. The fresh-install entrypoint refuses an existing Pods directory. Reinstalling an updated Podfile uses the original CocoaPods command under the same inherited-descriptor lock discipline. Host-only hook checking operates on disposable copies of an already installed fixture and never enters a namespace or runs native tools.

- `runtime/unreal-ios-pod-install-9upnq787/result.json`: first actual original-tool installation on stage106; it precedes the wrapper correction.

Only selected JSON metadata and authored source are selected for publication. Raw CocoaPods/Epic tool logs are explicitly excluded in `private_logs`; original generated Epic projects, original UE configuration files, proprietary tools and binaries, and the private runtime remain outside this package. Metadata paths and hashes identify private inputs without distributing their contents. The package specification is prepared for the repository's standard packaging step; this checkpoint itself does not publish a runtime overlay or advance the runtime selection.
