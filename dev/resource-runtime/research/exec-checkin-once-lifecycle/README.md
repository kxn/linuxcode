# Once-only exec/checkin lifecycle

The original UE Xcode/CocoaPods stage107 attempt reached 794 of 800 UBT actions. Two remaining original Clang processes were not compiling: each main thread yielded in the actual mapped mldr waiting for pthread initialization, while its new child waited for an explicit-checkin RPC reply. The live server had no corresponding child registry entries. Its selected message queues and the client socket queues were empty. Raw client/server captures, cores, binaries and Epic build logs are deliberately excluded.

The existing exec-pipe monitor can mark a process replacement after a new main-image checkin has already run. Previously every pthread checkin also executed the process replacement path. A late replacement flag could therefore make a pthread checkin unregister its own thread; the normal reply path then suppresses the reply for that dead thread. The exact native monitor/main/child event order was not traced. This is a demonstrated source defect which can reproduce the same self-unregistration and missing reply, not a claim that the native run's complete cause has been proven.

The fix retains the existing close-on-exec pipe and success/failure marker. The original monitor and main-thread checkin share the same once-only FD lease, protected by the existing Process lock. Main checkin consumes an already-ready pipe before reading the replacement flag; a late monitor cannot restore that flag or consume a newer exec's pipe. Only a main-thread checkin enters process lifecycle handling. The existing is_fork field determines whether to emit the parent's fork notification. A failure byte leaves the old task and responsibility intact, successful disclaim updates responsibility only after EOF, and native exec still uses notifyDead. No RPC ABI, new queue, busy wait or replacement scheduler is introduced.

## Verification and limits

The host regression compiles the real Call, Process and Thread sources with matching private headers. It uses real Linux pipes and dispatches the actual stored production monitor callbacks in controlled order. XNU object construction/destruction, transport and scheduling boundaries are controlled. All ten candidate cases pass. Exact stage107 archived source/header inputs fail the six expected race/notification cases while four normal-path controls pass. This is not a full historical-server binary, a native Darling session, or a real Linux exec test. Source digests match the complete stage108 server build and the regression report.

The fixed source was published as [577b168d4c9a3af676fd4c9e859d70d2f56924ee](https://github.com/kxn/darlingserver/commit/577b168d4c9a3af676fd4c9e859d70d2f56924ee) on the existing linuxcode/xcode-x86_64 fork branch. This package makes no further commit or push.

The confirmed-stalled stage107 build was subsequently interrupted deliberately. Its native Xcode status 65 and later Info.Template/rsync diagnostics describe an unfinished/cancelled build; they do not establish a separate template or rsync defect. A host observer's chmod failure was separate from the nonfatal server snapshot and did not itself end the native invocation. Stage108 v10 has now terminated with native Xcode status 75 / UBT OtherCompilationError. It reused the 794 completed actions, completed both previously stalled CoreUObject.13 and Niagara.13 compile actions among the remaining six actions, and reached action 3, Link. The original linker could not open a UBA temporary response file named through /var/root and its canonical /private/var/root alias. The private UBT log is not attached. This progress does not trace the earlier native lifecycle event order or prove that the lifecycle change was the sole cause. Full linking, App construction and signing still did not succeed. A v11 preparation record selects only the existing official UBA_ROOT environment option to put UBA storage/temp under the workspace; the original Xcode CLI and engine source are unchanged. That is a hypothesis comparison, not an adopted fix, and this package asserts no v11 result. S2C dead-target and exec-generation lifetime issues are also outside this fix.

## Reproduction inputs

Apply this overlay on the existing research/source baseline, including the earlier atomic XNU wait-handoff and S2C reply-transaction changes. The payload contains the three lifecycle edits, matching Thread/Call headers and source, the host fixture and C bridge, resolver with its digest dependency, and existing complete-server build/staging tools. Run scripts/probe-exec-checkin-lifecycle.py against a prepared runtime/darlingserver-source-build tree with its generated headers, Ninja commands and non-replaced object/archive inputs. Those build products must be rebuilt from the baseline or separately supplied; they are not shipped in this source-only package. The regression JSON records their precise hashes and commands.

The probe pins its negative control to runtime/remap-diagnostic-server-scqr1r7d/stage.json. Its changed historical Process/Call sources and Process header are attached through reference/source-history.json and the original-file map; unchanged Thread/Call inputs are present in payload. All manifests read by resolve-evidence-history.py are included as JSON references so old-input lookup has no missing-manifest shortcut. Restore references to their original workspace paths (unwrap the UTF-8 JSON text for historical source snapshots), and install reference/source-history.json as runtime/source-input-history/manifest.json in the restored workspace. Then resolve each expected stage107 digest exactly. Do not substitute the current source for a missing historical input. Stage108 build and artifacts108 records are provenance, not proof of a successful full UE build.

Only self-owned source and selected JSON evidence are attached. No core, executable, object/archive binary, SDK, Epic source/log, identity store, private key or authorization material is included.
