# Keep XPC connections alive through asynchronous reply delivery

The next focused asset run exposes a separate parent failure before the simulator agent is spawned: libxpc dmxh_async_reply_handler dereferences a connection's already disposed internal data pointer0xbadfeed. The captured source/disassembly accesses service_name through that invalid pointer while handling a disconnected reply. This run therefore does not establish whether the new synchronous workloop path passes in the original agent.

The private async reply context previously retained its block and queue but passed the connection to dispatch_mach as an unowned raw context. It now also owns the connection through actual reply/cancellation delivery, releasing that reference when the context is destroyed. The complete libxpc source build preserves the public export/reexport contract and is composed with the same server, stage72 kernel and paired pthread runtime in stage73. No default or mapped library is overwritten.

The independent native regression releases every client's public reference immediately after sending.32 server requests deliberately hold their real reply rights until all requests arrive;32 additional requests are explicitly cancelled. Every reply/cancellation callback runs exactly once while its connection is still alive, and all64 connection finalizers subsequently run exactly once. The old stage fails before receiving the delayed requests after releasing its clients; the corrected stage passes. This is an actual XPC/Mach communication and lifetime check, not a synthetic callback. It does not claim to exhaust every peer-failure/reconnect ordering.
