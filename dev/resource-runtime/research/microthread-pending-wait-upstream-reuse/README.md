# Preserve an armed XNU wait across internal lock resumes

Darling already supplies the XNU wait queues, pthread turnstiles and cooperative mutexes used by this path. The checked upstream HEAD (`89751e64bc6c2082f7725061824ee0e33395b0de`) matches our pinned vendor base. Its `dtape_thread_entering` clears `TH_WAIT` on every microthread resume, including an internal mutex resume after a real XNU wait was armed but before `thread_block`. The paired XNU `sched_prim.c::thread_unblock` instead clears those bits at the actual wake.

The small source repair preserves pending waits across internal resumes and adopts the existing XNU state update in `thread_unblock`. It keeps the existing queues, locks, wake path and previous wait-timer cancellation. [Source commit](https://github.com/kxn/darlingserver/commit/7578653dbec52131831766081c8a85158b028f60) is on the existing `linuxcode/xcode-x86_64` branch, authored as Comman Kang.

The attached Linux fixture links the actual duct-tape source functions and mutex implementation. Controlled scheduler hooks force an internal lock suspension between arming and blocking. Before the change, the wait returns `THREAD_WAITING` without ever suspending for its event (exit 1). With the change, it suspends until a genuine wake and returns `THREAD_AWAKENED`; a genuine wake before blocking also works (exit 0). This is a focused boundary regression, not complete scheduler or timer coverage. Run `python3 scripts/probe-microthread-pending-wait.py` in a developer workspace with the existing server build tree.

That run does not establish a complete UE project or App build. The private process core and full original compiler logs are not included.
